4Data Profiling (Provider Portal)~2–3 minutes

ON SCREEN

Click to Data Profiling tab. Select "Provider Portal".

SAY
Before we map anything to a canonical schema, we need to answer a different question: is the data in these fields actually usable? Mapping logged_at to EVENT_TIMESTAMP is pointless if half the timestamps are null or unparseable.

Point at the structural profile table:

This is a SQL-based profile — runs in milliseconds, costs nothing. For every field: null rates, cardinality, min/max values.

Look at content_assigned_to — only appears in 1 out of 10 events. Same with export_format. These are conditional fields — they only exist when the activity type is "content_activated" or "export." That's a real-world pattern your team deals with: sparse fields that break if you assume every event has the same shape.
ON SCREEN

Click "Run AI quality profiling".

SAY (while running)
Now we ask a cheaper model — mistral-large2 — to look at the actual events and flag what a data quality analyst would catch.

Results appear (4 findings). Read key ones:

Finding 1: export_format missing in non-export events. Makes sense, but downstream dashboards that assume this field always exists will break.

Finding 4: user_device has inconsistent values — desktop_chrome, mobile_safari, desktop_edge. The AI flagged that it's packing two dimensions into one field — device type AND browser. If you want to ask "what percentage of providers use mobile?" you'd need to parse this. The AI caught a design choice from the data alone.
ON SCREEN

Scroll to the cross-source comparison matrix.

And here's the forensic summary. Every row is a concept. Every column is a product. Look across any row: ts, event_time, occurred_at, timestamp, logged_at — all mean "when did this event happen."

This is your schema divergence, in one table.
Why this matters: The cross-source matrix is the most powerful visual in the demo. It makes the abstract problem concrete and undeniable. Jennifer can screenshot this for her next board deck. The profiling step also quietly demonstrates Snowflake doing what Monte Carlo and Atlan do — without naming them. Let Jennifer connect the dots herself.

5AI Mapping & Review~3–4 minutes

ON SCREEN

Click to AI Mapping & Review tab. Select "Waiting Room Displays".

SAY
We've profiled the data, we've classified the fields. Now the system answers the real question: where does each field land in a unified event schema?

Open the Rationale prompt expander briefly — just long enough to show it's there. Then collapse and click "Generate mapping suggestions".

SAY (while spinner runs)
Each field gets embedded — converted to a vector — and compared against 12 canonical event variables using cosine similarity. The system finds the best match, then asks the LLM to explain its reasoning.

Results appear. Walk through the three tiers:

Green: AUTO_APPROVED

96% confidence. ts maps to EVENT_TIMESTAMP. The system auto-approved this — it's already in the mapping repository. No human needed, no delay.

Orange: PENDING

78%. Is ad_unit_id a content reference or a campaign identifier? The AI has an opinion — read the rationale — but it's not confident enough to decide alone. It's asking a human. This is the governance moment.

Click Approve.

Yellow: NOVEL

Score below 70%. The system can't place this field. Maybe venue needs to become a new canonical field. Maybe it doesn't. That's a decision for your data governance team — the AI flagged it, humans decide.
KEY TRANSITION

Switch to "iXR Interactive Devices" and click "Generate mapping suggestions".

SAY (when blue MDR_MATCH cards appear)
See the blue ones? Those are MDR hits. kiosk_serial maps to the same DEVICE_ID that screen_id did from waiting room. The system remembered. No AI call, no embedding computation, 99% confidence, instant.

That's the compounding effect. The first source is the most expensive. Every source after that is cheaper and faster.
If anyone asks about thresholds: "85% for auto-approve, 70% for human review — stored in the config table, changeable anytime. Tighter governance? Raise them. More automation? Lower them. It's a dial, not a rewrite."
Note on misclassifications: If form_id or clinic_id auto-approved to the wrong target (the AI rationale says "not a correct match" but cosine score was high), use it as a talking point: "The AI is honest about its uncertainty — read the rationale. This is exactly why you need the human-in-the-loop. In production, we'd add a second gate: if the rationale contradicts the match, route to human review regardless of score."

Reframe for the room:

PatientPoint has five product lines today. But think about acquisitions, vendor changes, schema migrations. Every one is a "new source." Every one benefits from every mapping that came before it. The first source is the most expensive. Every source after that is cheaper and faster.
MDR Management: Use the source filter dropdown to review mappings per product. Bad auto-approves can be re-targeted via the inline dropdown or deleted — directly in the app, no SQL needed.

7Pipeline Builder (the finale)~2 minutes

ON SCREEN

Click to Pipeline Builder tab.

SAY
Everything so far has been interactive — forensic analysis, human review, iterative learning. That's the design-time workflow. But Jennifer, you said you need this running continuously. That's what this tab does.

Point at configuration controls (TARGET_LAG, warehouse, quality threshold):

These are the knobs. 10-minute lag means the unified view is never more than 10 minutes behind. For waiting room proof-of-play, that's fine. For programmatic bid events, you might want 1 minute. Each layer is independently configurable.

Scroll to the Gold Dynamic Table SQL:

Look at the SELECT expressions. RAW:ts::VARCHAR AS EVENT_TIMESTAMP for waiting room. RAW:event_time::VARCHAR AS EVENT_TIMESTAMP for iXR. Different JSON paths, same canonical column. Every expression was generated from the MDR — the mappings your team approved.

Add a new source next month? Run it through the workflow, approve the mappings, the Gold DT SQL regenerates automatically. No one rewrites ETL.
